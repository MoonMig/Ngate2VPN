# Changelog

Все значимые изменения проекта документируются в этом файле.

Формат основан на [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/),

## [4.00] — 2026-09-24

### Добавлено
- **Таймаут 2FA распознаётся отдельно.** Парольный вход, который шлюз отклонил через ~8 с и дольше (шлюз ждёт подтверждения ~15 с), теперь даёт ошибку «Two-factor confirmation timed out» вместо «Invalid credentials». Автоповтор — ровно 2 попытки (первая и один повтор, каждый шлёт новый push), затем пауза, запись в журнал и алерт. Быстрый отказ по-прежнему считается неверным паролем.
- **Проверка системного прокси при подключении.** Клиент ходит к шлюзам через системный прокси; если он не работает, попытки раньше заканчивались невнятным `exit code: 0`. Теперь при каждом старте в фоне проверяется путь до шлюза (реальный `CONNECT` через прокси с учётом списка исключений), и при сбое в журнале появляется предупреждение с именем прокси и подсказкой добавить шлюз в исключения. Ошибки `ProxyConnectionClosedError` / «connection with proxy closed prematurely» классифицируются как повторяемая ошибка `proxyFailure`.
- **Трей: область «Active connections».** Между списком профилей и «Settings…» показываются имя и IP каждого подключённого туннеля. Клик по строке копирует IP, показывает «Copied» и не закрывает меню; подсказка «Click to copy the IP address» (собственная панель — меню не рисует подсказки для таких пунктов). Подсветка строки надёжно снимается.
- Главное окно: клик по IP-бейджу подключённого туннеля копирует адрес (кратко «Copied»).
- Тесты: `WatchdogPolicyTests` (backoff, лимиты, бюджет 2FA, таймаут старта), `PersistenceAndProxyTests`, расширены тесты парсера. Всего 63 теста.

### Изменено
- **Лимит автоповторов для Auto-reconnect.** Раньше у туннелей с Auto-reconnect предела не было (в журнале — попытки до №58 за 14 часов при сломанном прокси). Теперь 24 подряд идущие неудачи (~5 ч бодрствования при паузе до 15 мин), затем пауза и алерт; пауза сбрасывается после пробуждения из сна. Без Auto-reconnect по-прежнему 8.
- **Логика watchdog вынесена в `WatchdogPolicy.swift`** (чистые функции: пауза между попытками, лимиты, 2FA-бюджет, таймаут старта, повтор при старте) — покрыта юнит-тестами.
- **Рефакторинг файлов.** `AppState.swift` разбит на `AppState+Connection/Watchdog/Prewarm/Logging/Alerts/Secrets` и `TunnelModels.swift`; `ContentView.swift` — на `HomeView`, `EditSheet`, `JournalView`, `LogTextView`, `SettingsView`, `Components`, `DesignSystem`. Поведение не менялось.
- Главное окно: клик по строке туннеля больше не открывает настройки (профиль редактируется через правый клик → Edit Profile). Меню правого клика теперь настоящее `NSMenu`, пункт «Delete Profile» красный (SwiftUI `.contextMenu` цвет текста игнорирует).
- Вкладка «Настройки»: под кнопками вкладок добавлена полупрозрачная полоса (30% прозрачности), чтобы прокручиваемый текст не просвечивал за ними.
- Переключение вкладок без неявной анимации (при первом показе вкладки мелькал пустой прямоугольник).

### Исправлено
- **Профили могли пропасть при обновлении.** Новое поле в модели делало сохранённые данные нечитаемыми, и приложение стартовало без профилей. Теперь чтение терпимо к отсутствующим полям, а перед перезаписью предыдущая версия сохраняется в резервную копию (`…previous`, нечитаемое — `…undecodable`; значения `pinCode`/`password` в копиях обнуляются).
- **Миграция секретов из очень старых профилей не срабатывала:** профили очищались от PIN/пароля до вызова миграции. Порядок исправлен.
- **`/etc/resolver` принадлежал пользователю** (мог быть подменён без sudo). Установка и helper теперь делают `chown root:wheel`. **После обновления DNS Helper потребует переустановки** (Settings → DNS Helper; один запрос пароля администратора) — код helper изменился.
- Устаревшие комментарии (`NEDNSSettingsManager`, ключи ini, файл `/etc/resolver/.`), предупреждение компилятора про `weak self`.

## [3.28] — 2026-09-20

### Исправлено
- **Прогретый туннель «сразу выключался» после долгого простоя.** `ngateconsoleclient` запускает таймер входа при старте сессии (до нашего шлюза) и через ~2 мин отказывается («Transaction timeout happened while connecting to gate»), поэтому клиент, прогретый час назад, завершался в момент Connect, и включить туннель удавалось только со второго раза.
  - Прогретым клиентам в конфиг добавляется `operationsTimeout=1200000` (миллисекунды; `connectionsTimeout` не помогает).
  - Прогретые клиенты обновляются каждые 10 минут (проверка в каждом проходе watchdog), чтобы они всегда укладывались в этот запас и адоптированные туннели не жили с огромным таймаутом.
  - Страховка: если адоптированный клиент всё же умер в первые 30 с, не дойдя до подключения, и реальной ошибки нет, приложение один раз само запускает свежий клиент.
  - Сообщения о таймауте входа теперь распознаются как повторяемая ошибка (`startupTimeout`).

## [3.27] — 2026-09-20

### Изменено
- **Один запрос Keychain на все туннели.** PIN и пароли всех туннелей теперь лежат в одном элементе Keychain (`vault.v1`) и читаются один раз при первом обращении, вместо отдельного элемента (и отдельного запроса пароля) на каждый секрет. Старые элементы (`<id>_pin`, `<id>_password`) переносятся автоматически при первом запуске и удаляются; при отказе в доступе миграция откладывается без потери данных.

### Добавлено
- **Стабильная подпись сборок.** `Scripts/setup-signing-identity.sh` один раз создаёт локальный самоподписанный сертификат подписи кода; `build-app.sh` подписывает им сборки (иначе — ad-hoc, как раньше). Подпись больше не меняется от сборки к сборке, поэтому «Always Allow» для Keychain переживает обновления.

## [3.26] — 2026-09-20

### Изменено
- **Туннели с логином/паролем больше не прогреваются.** Они запускаются в песочнице без токена (инициализация ~0,3 с, подключение ~2 с), поэтому прогрев выигрывал доли секунды, но держал простаивающий процесс с файлом пароля на диске, читал Keychain при запуске и занимал очередь прогрева. Прогреваются только туннели, которым нужен токен (по сертификату, а также парольные при `disableTokenSandbox`).
- Connect All: туннели, не использующие токен, стартуют сразу и не участвуют в ступенчатой задержке 3 с.

## [3.25] — 2026-09-19

### Добавлено
- **Предварительный прогрев туннелей (Pre-warm tunnels).**
  - `ngateconsoleclient` тратит ~12 с на чтение всех контейнеров токена до подключения. Теперь клиенты запускаются заранее (при старте приложения, при вставке токена, после пробуждения из сна и сразу при нажатии Disconnect — замена прогревается параллельно с остановкой старого клиента, поэтому повторное подключение тоже быстрое) и удерживаются перед первым сетевым подключением. По Connect уже инициализированный процесс сразу отпускается, и туннель поднимается за секунды.
  - Удержание реализовано маленькой библиотекой `libngategate.dylib` (`Support/ngategate.c`), которая через `DYLD_INSERT_LIBRARIES` перехватывает `connect()` для IP-сокетов и ждёт файла-сигнала. Бинарник клиента не изменяется. Если приложение завершилось, удерживаемый клиент сам завершается.
  - Прогретые процессы хранятся отдельно от рабочих и не видны watchdog'у и статусам, пока Connect не «усыновит» один из них. Изменённый профиль/пароль сбрасывает прогретый процесс (сверка по SHA-256 настроек).
  - Туннели по сертификату прогреваются только при вставленном токене (USB CCID-интерфейс, отслеживание через IOKit); извлечение токена и сон сбрасывают прогретые процессы.
  - Connect All: прогретые туннели стартуют сразу, ступенчатый запуск (3 с) применяется только к холодным.
  - Настройка: Settings → Application → «Pre-warm tunnels (faster connect)» (по умолчанию включена). Без `libngategate.dylib` в бандле (например `swift run`) прогрев недоступен.

### Исправлено
- Файл с учётными данными клиента мог остаться на диске, если процесс завершался, когда `TunnelProcess` уже был освобождён (обработчик завершения держал его слабой ссылкой). Имена временных конфигов теперь уникальны для каждого запуска.

## [3.24] — 2026-09-19

### Улучшено
- **Туннели с логином/паролем больше не читают смарт-карту при старте.**
  - `ngateconsoleclient` при запуске перебирает все контейнеры токена (JaCarta: ~12 с на процесс; токен — последовательный ресурс, общий для всех процессов клиента), даже если туннелю по паролю токен не нужен, и при этом задерживает сертификатные туннели.
  - Теперь клиент для туннелей с аутентификацией по паролю запускается через `sandbox-exec` с профилем, который закрывает доступ к `com.apple.ctkpcscd` и фреймворку `jcPKCS11-2`. Инициализация хранилища у такого процесса — 0,3 с вместо ~12 с и больше, туннель по паролю поднимается за ~2 с.
  - Connect All для трёх туннелей (парольный + два по сертификату): ~35 с вместо ~43 с.
  - Настройки CryptoPro и считыватели не затрагиваются; сертификатные туннели запускаются как раньше.
  - Отключение: `defaults write com.ngate2vpn.app disableTokenSandbox -bool YES`. Если `/usr/bin/sandbox-exec` недоступен, клиент запускается без песочницы.

## [3.21] — 2026-06-22

### Исправлено
- **Auto-reconnect не срабатывал после выхода из сна.**
  После sleep/wake watchdog может выполниться раньше, чем завершится асинхронный `handleExit` (оба работают на `@MainActor`, но `handleExit` диспатчится как `Task`). В этот момент watchdog видел `isNgateReconnecting == true` (флаг ещё не сброшен), а процесса уже нет — и пропускал туннель без попытки переподключения. Двойное исправление:
  1. `runWatchdogPass` теперь явно сбрасывает `isNgateReconnecting = false` при `processState == nil` — независимо от того, успел ли `handleExit` это сделать раньше.
  2. Новый обработчик `NSWorkspace.didWakeNotification`: при выходе из сна немедленно сбрасывает `isNgateReconnecting` для всех туннелей с мёртвым процессом и запускает внеплановый проход watchdog (не ждёт следующего тика через 5 с).

## [3.20] — 2026-06-22

### Исправлено
- **Auto-reconnect не работал после обрыва сети — переподключение не происходило.**
  Когда ngate логирует retryable-ошибку (`connectionRefused`, `sessionRefreshFailed` и т.п.) во время активного соединения, флаг `isNgateReconnecting` выставляется в `true` — это сигнал watchdog'у не вмешиваться, пока ngate сам пытается восстановить сессию. Проблема: если процесс ngate завершался до того, как успевал вывести `"vpn online"`, флаг оставался `true`, а `transitionState(.failed)` его не сбрасывал (сброс был только для `.stopped`). На каждом тике watchdog видел `isNgateReconnecting == true` и пропускал туннель навсегда. Исправлено: `handleExit` сбрасывает флаг перед переходом в `.failed` — процесса больше нет, некому reconnecting делать.

## [3.19] — 2026-06-22

### Добавлено
- **Переключатель Auto-reconnect в настройках каждого профиля.**
  Когда включён: watchdog переподключает туннель после любого неожиданного разрыва (обрыв сети, падение процесса) без ограничения числа попыток. Экспоненциальный backoff сохраняется (5 с → 10 с → … → 15 мин), чтобы не спамить сервер. Ручное отключение через UI никогда не триггерит переподключение — туннель остаётся в состоянии `.stopped`. Config-ошибки (неверные credentials, cert не найден, mismatch hostname, неверный URL) тоже не вызывают переподключение — в этих случаях повторная попытка заведомо не поможет.
  
  Когда выключен: поведение watchdog не меняется (circuit breaker на 8 попыток, только retryable-ошибки).

## [3.18] — 2026-06-19

### Исправлено
- **DNS не применялся из-за рекурсивной порчи JSON-буфера.**
  `appendSystemLog` вызывает `appendLog`, который вызывает `feedDNSParser`. Если `feedDNSParser` эмитировал диагностическое событие ("DNS: JSON block detected") прямо в момент активного захвата JSON (`capturing=true`), system-log строка рекурсивно попадала обратно в `feedDNSParser` и добавлялась в буфер как JSON-контент. В результате буфер содержал `{↵[PROFILE] DNS: JSON block detected, reading…↵"GateAddresses" : []…`, `JSONSerialization` отказывал, и DNS не применялся. Исправление: `appendLog` пропускает вызов `feedDNSParser` для строк, содержащих `[SYSTEM]` (все system-log строки генерируются нами, а не ngateconsoleclient).

## [3.17] — 2026-06-19

### Исправлено
- **DNS не применялся для профилей, где ngateconsoleclient выводит HTTP-ответ gateway в формате `Debug     <строка>` без предшествующего временно́го штампа.**
  `strip()` искал ` Debug` (с пробелом перед словом) и не находил `Debug` в позиции 0. Fallback `?? line` подставлял сырую строку целиком, и в буфер попадал текст вида `Debug         "GateAddresses" : []` — невалидный JSON, который `JSONSerialization` молча отвергал. Добавлена anchored-проверка: если строка начинается с ключевого слова уровня (`debug`/`info`/`warning`/`error`) без пробела перед ним, оно корректно отсекается.

## [3.16] — 2026-06-19

### Исправлено
- **DNS не применялся для профилей где gateway возвращает DNSs/SearchDomains не внутри IPTunnels[], а на другом уровне JSON.**
  Прежний `parse()` искал DNS только строго внутри `obj["IPTunnels"][N]["DNSs"]`. Некоторые CheckPoint gateway возвращают DNS на верхнем уровне JSON-объекта (`obj["DNSs"]`, `obj["SearchDomains"]`) или в другой вложенности. Теперь `collectDNS()` рекурсивно обходит всё дерево JSON и собирает все встреченные `"DNSs"` и `"SearchDomains"` вне зависимости от уровня вложенности.

## [3.15] — 2026-06-19

### Исправлено
- **Логи туннелей писались в `NgateVPN/logs/` вместо `Ngate2VPN/logs/`** — устаревшее имя директории в `FileLogger`. Теперь оба компонента (FileLogger и DNSApplier) используют единый путь `~/Library/Application Support/Ngate2VPN/`. Директория `NgateVPN/` в Application Support больше не создаётся.

### Улучшено
- **Диагностика DNS-парсера** — три новых `[SYSTEM]`-события в журнале туннеля:
  - `DNS: JSON block detected, reading…` — JSON-блок от gateway обнаружен и парсер начал его читать.
  - `DNS: JSON block parsed but no tunnel data found` — блок прочитан, но поле `DNSs` пустое или отсутствует.
  - `DNS parsed from gateway — servers: …; domains: …` — данные успешно извлечены (существующее событие, теперь дополнено предупреждением если `servers: none`).
  
  Если после подключения ни одно из этих событий не появляется — JSON-блок вообще не попадает в парсер.

## [3.14] — 2026-06-19

### Исправлено
- **DNS-парсер пропускал JSON-блок gateway для некоторых профилей.**
  Ключевое исправление: парсер теперь обрабатывает строки НЕЗАВИСИМО от лог-уровня:
  1. `strip()` расширен до всех стандартных уровней (`Info`, `Warning`, `Error`) в дополнение к `Debug`, с проверкой границы слова (следующий символ — пробел/таб) чтобы не матчить "Info" внутри слов.
  2. Если никакой известный лог-уровень не найден, `feed()` использует сырую строку как payload. Некоторые версии ngateconsoleclient выводят JSON-блок как чистый текст без лог-префикса — без этого fallback весь блок молча игнорировался.

## [3.13] — 2026-06-19

### Исправлено
- **DNS Helper не срабатывал для одного из профилей — ни файлов `/etc/resolver/`, ни событий `[SYSTEM]` в логах.**
  `NgateGatewayResponseParser` игнорировал Debug-строки, если:
  (1) уровень логирования имел другой регистр (`debug`, `DEBUG`) — исправлено case-insensitive поиском;
  (2) JSON-блок начинался не с первого символа payload, а после текстового префикса (`Gateway response: {…}`) — исправлено поиском `{` в любом месте строки; brace-трекинг начинается именно с найденного `{`.
  Добавлено диагностическое `[SYSTEM]`-событие «DNS parsed from gateway» в лог туннеля при каждом успешном парсинге JSON-блока — позволяет сразу определить, доходит ли ответ gateway до парсера.

## [3.12] — 2026-06-19

### Исправлено
- **DNS Helper: SearchDomains второго туннеля не всегда применялись.**
  Если gateway возвращал несколько записей в `IPTunnels[]`, функция `feedDNSParser`
  вызывала `dnsPolicy.upsert()` отдельно для каждой записи с одним и тем же `tunnelID`.
  Каждый последующий вызов перезаписывал предыдущий: домены из ранних записей терялись,
  а если последняя запись содержала пустые `DNSs` — конфиг удалялся полностью.
  Теперь все записи агрегируются через `flatMap` в один вызов `upsert()`.

## [3.11] — 2026-05-30

## [2.39] — 2026-05-14

### Исправлено

## [2.10 (1)] — 2026-05-06

### Изменено
- **`FileLogger` переписан на `AsyncStream` с одним consumer task'ом.**
  Раньше каждая строка лога создавала новый `Task { await ... }`. При
  включённом `-vvvv` режиме ngate с несколькими активными туннелями
  это означало десятки тысяч короткоживущих Task'ов в минуту — каждый
  аллоцировал свой continuation frame, попадал в очередь cooperative
  pool, конкурировал за executor актора. Теперь у каждого FileLogger
  один long-running consumer Task, который в `for await` цикле
  вычитывает строки из stream и передаёт их в `LogWriterActor`.

### Преимущества
- **Гарантированный FIFO порядок.** Строки попадают на диск ровно в
  том порядке, в котором были вызваны `append()`. Раньше две Task'и,
  suspend'нувшиеся на одном await, могли resume'нуться не по порядку.
- **Меньше нагрузки на runtime scheduler.** Ноль аллокаций Task'ов на
  hot path — `continuation.yield()` это просто atomic enqueue.
- **Backpressure protection.** Stream имеет bounded buffer на 4 096
  строк с политикой `bufferingNewest` — если диск замедлится или
  ngate выдаст пиковый burst, старые строки отбрасываются вместо
  неограниченного роста памяти. В нормальной работе буфер пустой.
- **Чистый shutdown.** В `deinit` вызывается `continuation.finish()`,
  consumer Task завершается естественно, актор и handle освобождаются.

## [2.9 (1)] — 2026-05-06

### Изменено
- **Расширен in-memory буфер журнала.** Раньше каждое подключение
  хранило только последние 200 строк лога — при `-vvvv` режиме ngate
  это означало терять историю каждые несколько секунд. Лимит поднят
  до **30 000 строк на туннель** + **5 000 строк системных событий**
  (≈ 1–3 часа `-vvvv` вывода). Лимит безопасен потому что в 2.6 был
  внедрён инкрементальный рендеринг — добавление строки больше не O(N)
  по размеру журнала.
- **Amortised trimming.** Буфер трим'ится только когда переполняется
  на `slack` (1 000) элементов сверх лимита, а не на каждое
  превышение. Это превращает overhead с O(N) на каждый append в
  амортизированно константный.
- **Fast-path для отображения журнала с одним выбранным туннелем.**
  Когда юзер смотрит один туннель И System выключен, все entries
  идут из одного источника в правильном порядке — sort пропускается
  целиком, экономится ~N·log(N) сравнений на каждый render. На
  заполненном буфере 30 k строк это десятки миллисекунд.

### Контекст
- Старые строки остаются на диске через `FileLogger` (5 МБ ротация,
  30 дней хранения). UI журнала показывает только то что в RAM —
  ничего не потеряно, просто старое не отображается.
- Пять активных туннелей с заполненными буферами ≈ 15 МБ RAM, что
  соизмеримо с 1 кадром React-приложения.

  `sudoers.d` запись перед установкой.
